
# DHCP Snooping — Rogue DHCP Server Attack Prevention on a Layer 2 Switch

---

## 1. Lab Title

**DHCP Snooping: Blocking Rogue DHCP Servers and Protecting Clients from IP Address Spoofing**

---

## 2. Lab Objective

This lab demonstrates how to configure **DHCP Snooping** on a Cisco Layer 2 switch to protect network clients from rogue (unauthorized) DHCP servers. The lab simulates a real-world attack scenario where a fake DHCP server exists on the network with the same IP address as the legitimate server, and shows how DHCP Snooping enforces trust boundaries to ensure only the legitimate server can assign IP addresses to clients.

**Skills and concepts practiced:**

- Enabling DHCP Snooping globally on a switch
- Configuring DHCP Snooping on a specific VLAN
- Defining trusted and untrusted ports based on network role
- Configuring a router interface as the legitimate DHCP server gateway
- Understanding how DHCP Snooping drops DHCP offers from untrusted ports
- Recognizing the attack scenario: two servers with identical IPs on the same network

---

## 3. Concept Explanation

### What is DHCP Snooping?

**DHCP Snooping** is a Layer 2 security feature on Cisco switches that acts as a firewall between untrusted hosts and trusted DHCP servers. It intercepts and inspects all DHCP messages on the switch, allowing DHCP responses (OFFER, ACK, NAK) only from ports designated as **trusted**. All other ports are **untrusted** by default and can only send DHCP requests (DISCOVER, REQUEST) — never responses.

### The Attack This Lab Addresses

Without DHCP Snooping, any device connected to the switch can act as a DHCP server. The topology in this lab includes:

- **Main Server (Server4):** IP 10.0.0.100 — the legitimate DHCP server
- **Fake Server (Server5):** IP 10.0.0.100 — a rogue device with the same IP, attempting to respond to client DHCP requests

When a client broadcasts a DHCP DISCOVER, both servers may respond. If the fake server responds first, the client receives a DHCP lease from the attacker. The attacker can then:

- Assign themselves as the **default gateway** (man-in-the-middle attack — all client traffic flows through the attacker)
- Assign a malicious **DNS server** (DNS hijacking)
- Exhaust the legitimate IP pool (DHCP starvation)

### How DHCP Snooping Works Internally

1. DHCP Snooping is enabled globally and on specific VLANs.
2. The administrator designates the port connected to the legitimate DHCP server (or the uplink to the router acting as DHCP relay) as **trusted**.
3. All other ports remain **untrusted** by default.
4. When a DHCP OFFER or ACK arrives on an untrusted port, the switch **drops the frame silently** — it never reaches the client.
5. DHCP requests from clients on untrusted ports are still forwarded normally toward the trusted port direction.
6. The switch maintains a **DHCP Snooping Binding Table** — a record of MAC address, IP address, VLAN, and port for each leased address. This table is also used by Dynamic ARP Inspection (DAI) for further protection.

### Real-World Example

A hospital network has a legitimate DHCP server managed by IT. A visitor plugs in a personal hotspot device that also runs a DHCP server. Without DHCP Snooping, nurses' laptops could receive IP addresses and gateway information from the visitor's hotspot, routing all patient data through an unauthorized device. DHCP Snooping ensures the visitor's device's DHCP responses are silently dropped at the switch port.

### Advantages

- Prevents rogue DHCP server attacks with minimal configuration
- Creates the DHCP Snooping Binding Table, which is required for Dynamic ARP Inspection (DAI) and IP Source Guard
- Operates transparently — legitimate traffic is unaffected
- Can be applied per-VLAN for granular control

### Limitations

- Must be configured on every switch in the Layer 2 path — a switch without DHCP Snooping in the middle can still pass rogue DHCP responses
- DHCP Snooping binding table is lost on reload unless `ip dhcp snooping database` is configured to write to a persistent location (flash or TFTP)
- Incorrectly marking a legitimate server's port as untrusted will block all DHCP responses — clients will fail to obtain IP addresses

## 5. Step-by-Step Configuration

---

### Device: Switch1 — DHCP Snooping Configuration

#### Step 1 — Enable DHCP Snooping Globally

```bash
Switch> en
Switch# conf t
Switch(config)# ip dhcp snooping
```
**Explanation:** Enables DHCP Snooping globally on the switch. This activates the feature but does not yet enforce it on any VLAN — that requires a separate per-VLAN command. Without this global enable, no DHCP Snooping filtering occurs regardless of other settings.

> **Note:** An attempt to apply `ip dhcp snooping trust` at the global level was made in the raw log and rejected:
> ```
> Switch(config)# ip dhcp snooping trust
>                 ^
> % Invalid input detected at '^' marker.
> ```
> `ip dhcp snooping trust` is an **interface-level** command — it must be applied under a specific interface, not in global configuration mode. See Troubleshooting section.

#### Step 2 — Mark the Legitimate Server Port as Trusted (Fa0/4)

```bash
Switch(config)# int fa0/4
Switch(config-if)# ip dhcp snooping trust
Switch(config-if)# exit
```
**Explanation:** Designates Fa0/4 (connected to the Main Server — Server4) as a trusted port. DHCP OFFER and ACK messages arriving on this port will be forwarded normally to clients. This is the only port through which legitimate DHCP responses should arrive from the server side.

Without this command, even the legitimate server's DHCP responses would be dropped — clients would receive no IP addresses.

#### Step 3 — Enable DHCP Snooping on VLAN 1

```bash
Switch(config)# ip dhcp snooping vlan 1
```
**Explanation:** Activates DHCP Snooping enforcement on VLAN 1. DHCP Snooping must be enabled both globally (Step 1) and per-VLAN. Enabling globally without specifying a VLAN does nothing. All devices in this lab are on VLAN 1 (the default VLAN), so this single command covers the entire topology.

In a multi-VLAN environment, this command would be repeated for each VLAN requiring protection (e.g., `ip dhcp snooping vlan 10,20,30`).

#### Step 4 — Mark the Router Uplink as Trusted (Fa0/6)

```bash
Switch(config)# int fa0/6
Switch(config-if)# ip dhcp snooping trust
Switch(config-if)# exit
```
**Explanation:** Designates Fa0/6 (connected to Router1's Gi0/0) as a trusted port. In networks where the router acts as a DHCP relay agent (`ip helper-address`), DHCP responses arrive back through the router interface. Marking this uplink as trusted ensures relayed DHCP responses from a legitimate remote DHCP server are not dropped.

Even if the router is not acting as a relay in this specific lab, uplinks to routers and distribution switches should always be trusted ports as a general rule.

#### Step 5 — Confirm DHCP Snooping VLAN (Repeated Command)

```bash
Switch(config)# ip dhcp snooping vlan 1
```
**Explanation:** This command was entered a second time in the configuration log. This is idempotent — re-entering it has no effect if VLAN 1 is already in the snooping list. The final state is the same as after Step 3. No harm is caused by the repetition.

---

### Device: Router1 — Gateway Configuration

```bash
Router> enable
Router# configure terminal
Router(config)# interface GigabitEthernet0/0
Router(config-if)# ip address 10.0.0.1 255.0.0.0
Router(config-if)# no shutdown
```
**Explanation:** Assigns IP address 10.0.0.1/8 to the router's Gi0/0 interface — the interface connected to Switch1 Fa0/6. This IP serves as the **default gateway** for all devices on the 10.0.0.0/8 network. `no shutdown` activates the interface, which is administratively down by default on Cisco routers.

> **Note:** No additional DHCP relay (`ip helper-address`) or DHCP pool configuration was provided in the router's input. The router configuration in this lab is limited to the gateway interface. Full DHCP relay or server configuration was **Not Provided in Input**.

## 7. Troubleshooting

### Issue 1: `ip dhcp snooping trust` Applied at Global Level — Rejected

**What Happened:**
```
Switch(config)# ip dhcp snooping trust
                ^
% Invalid input detected at '^' marker.
```

**Root Cause:** `ip dhcp snooping trust` is an **interface subcommand** — it can only be applied under a specific interface configuration context (`Switch(config-if)#`). It does not exist as a global configuration command. The engineer attempted to apply it in global config mode.

**Fix Applied:** The engineer entered `int fa0/4` first to enter interface configuration mode, then applied `ip dhcp snooping trust` correctly.

**Lesson Learned:** Always confirm the correct configuration context before entering IOS commands. DHCP Snooping has two distinct levels: `ip dhcp snooping` and `ip dhcp snooping vlan X` are global commands; `ip dhcp snooping trust` and `ip dhcp snooping limit rate` are interface commands.

---

### Issue 2: Incorrect Interface Navigation Attempts

**What Happened:**
```
Switch(config)# int dhcp snoo
Switch(config)# int dhcp snoo
Switch(config)# int dhcp snoop
```

**Root Cause:** After exiting the Fa0/4 interface, the engineer appears to have typed `int dhcp snoo` — attempting to enter an interface named "dhcp snoo" which does not exist. The intent was to type `ip dhcp snooping vlan 1` but the commands were entered in the wrong order or with incorrect syntax.

**Fix Applied:** The engineer navigated to `int fa0/6` correctly on the subsequent attempt and applied the trust command there.

**Lesson Learned:** When CLI commands are not working as expected, pause and re-read the current prompt context (`Switch(config)#` vs `Switch(config-if)#`). The prompt always shows the current configuration context.

---

### Issue 3: `ip dhcp snooping vlan 1` Entered Twice

**What Happened:** The command was entered after configuring Fa0/4 trusted and again after configuring Fa0/6 trusted.

**Root Cause:** Navigation confusion during configuration. The second entry was redundant.

**Impact:** None — the command is idempotent. Re-entering it does not cause errors or change behavior.

## 8. Conclusion

This lab demonstrated how DHCP Snooping provides a targeted, low-configuration defense against rogue DHCP server attacks on a Layer 2 network. The key outcomes were:

- **DHCP Snooping globally enabled** activates the feature but requires per-VLAN configuration to enforce filtering.
- **Trusted port designation** is the core of DHCP Snooping — only ports explicitly marked as trusted can send DHCP server responses. The legitimate server port (Fa0/4) and the router uplink (Fa0/6) are the correct trust points in this topology.
- **The fake server (Server5)**, despite having the same IP address as the legitimate server, is connected to an untrusted port. Its DHCP OFFER messages are silently dropped at the switch — clients never see the rogue server's responses.
- **The DHCP Snooping Binding Table** is a byproduct of this configuration and enables further security features (DAI, IP Source Guard) without additional effort.
- The lab reinforced that `ip dhcp snooping trust` is an **interface-level** command — a common point of confusion for engineers new to this feature.

## 9. Notes / Real-World Insights

### Best Practices

- **Enable DHCP Snooping on all VLANs that have DHCP clients,** not just VLAN 1. In a production multi-VLAN network:
  ```bash
  ip dhcp snooping vlan 10,20,30,40
  ```

- **Always mark uplinks and trunk ports as trusted.** Any port connecting to another switch, a router, or a DHCP server must be trusted. Forgetting to trust an uplink breaks DHCP for all devices downstream.

- **Enable the DHCP Snooping database agent** to persist the binding table across reloads:
  ```bash
  ip dhcp snooping database flash:/dhcp-snooping.db
  ```
  Without this, the binding table is lost on every reload — breaking Dynamic ARP Inspection for existing clients until leases are renewed.

- **Set rate limits on untrusted ports** to prevent DHCP starvation attacks:
  ```bash
  interface fa0/2
  ip dhcp snooping limit rate 15
  ```
  This limits any single untrusted port to 15 DHCP packets per second — enough for normal clients but not for an attacker flooding DHCP DISCOVERs to exhaust the address pool.

- **Disable the `option 82` insertion if it causes issues with certain DHCP servers:**
  ```bash
  no ip dhcp snooping information option
  ```
  By default, DHCP Snooping inserts Option 82 (relay agent information) into DHCP requests. Some DHCP servers reject packets with Option 82 if they are not expecting it — causing clients to fail to get addresses even with correct snooping configuration.

### Common Mistakes

| Mistake | Consequence |
|---|---|
| Enabling DHCP Snooping globally but forgetting `ip dhcp snooping vlan X` | No DHCP filtering occurs on any VLAN — feature appears enabled but does nothing |
| Forgetting to trust the legitimate server's port | All DHCP responses are dropped — all clients fail to get IP addresses |
| Forgetting to trust uplink/trunk ports in a multi-switch topology | DHCP responses from a legitimate server on another switch never reach clients |
| Applying `ip dhcp snooping trust` in global config mode | Command rejected with invalid input error |
| Not configuring DHCP Snooping database persistence | Binding table lost on reload — DAI breaks for all existing clients |
| Not setting rate limits on untrusted ports | DHCP starvation attacks (e.g., Gobbler tool) can exhaust the DHCP pool |

### The DHCP Attack Landscape

| Attack | Description | DHCP Snooping Mitigation |
|---|---|---|
| Rogue DHCP Server | Attacker runs a DHCP server, assigns malicious gateway/DNS | DHCP responses on untrusted ports dropped |
| DHCP Starvation | Attacker floods DISCOVER with spoofed MACs to exhaust the pool | Rate limiting on untrusted ports (`limit rate`) |
| Man-in-the-Middle via DHCP | Rogue server assigns attacker as default gateway | Rogue server's OFFERs dropped by snooping |

### DHCP Snooping as a Foundation for Other Controls

DHCP Snooping is not just a standalone feature — it is the **prerequisite** for two additional Layer 2 security controls that build on the binding table it creates:

1. **Dynamic ARP Inspection (DAI)** — Uses the DHCP Snooping Binding Table to validate ARP packets. If an ARP reply claims a MAC-to-IP mapping that is not in the binding table, it is dropped — preventing ARP poisoning/spoofing attacks.

2. **IP Source Guard** — Uses the binding table to ensure that only packets with source IP and MAC addresses matching a valid binding entry are forwarded from an interface. Prevents IP address spoofing.

The full Layer 2 client protection stack is: **DHCP Snooping → DAI → IP Source Guard**.

### Interview and Job Tips

- "What is DHCP Snooping and what attack does it prevent?" — Know both the rogue server attack and DHCP starvation. DHCP Snooping directly prevents rogue servers; rate limiting on untrusted ports addresses starvation.
- Know the two configuration levels: global enable (`ip dhcp snooping`) + VLAN enable (`ip dhcp snooping vlan X`) + interface trust (`ip dhcp snooping trust`). Being able to recite these three steps in order shows practical command knowledge.
- Understand the Option 82 behavior — many engineers hit the "clients not getting IPs even with snooping configured" problem and it is almost always Option 82 being rejected by the DHCP server.
- Be able to explain what the DHCP Snooping Binding Table is and why DAI requires it — this shows awareness of the layered security model rather than just isolated feature knowledge.
