# Secure Remote Switch Management via SSH with RIPv2 Dynamic Routing

## 1. Lab Title

**SSH-Based Remote Access: Configuring Secure Switch Management with RSA Key Generation, Local Authentication, and RIPv2 Dynamic Routing**

## 2. Lab Objective

This lab demonstrates how to securely configure remote management access to a Cisco Layer 2 switch using **SSH (Secure Shell)** across a routed network. It also covers **RIPv2** dynamic routing between two routers so that an ADMIN PC on a remote network can reach the switch's management interface.

The lab builds on the concepts of the previous Telnet lab and upgrades them to an encrypted, production-appropriate management protocol.

**Skills and concepts practiced:**

- Configuring RIPv2 dynamic routing on two routers with `no auto-summary`
- Configuring a management SVI and default gateway on a Layer 2 switch
- Creating privileged-level local user accounts with `secret` (hashed) passwords
- Generating RSA key pairs for SSH encryption
- Configuring VTY lines for SSH-only access with local authentication
- Understanding the difference between `password` and `secret` in local user accounts
- Verifying SSH connectivity from a remote PC across a multi-hop routed network

## 3. Concept Explanation

### What is SSH and Why Does It Replace Telnet?

**SSH (Secure Shell)** is a cryptographic network protocol used for secure remote CLI access to network devices over TCP port 22. It is the direct, secure replacement for Telnet.

The fundamental difference is encryption:

| Feature | Telnet | SSH |
|---|---|---|
| Data transmission | Plaintext | Encrypted |
| Password exposure | Visible in packet captures | Protected by encryption |
| Port | TCP 23 | TCP 22 |
| Production use | No — deprecated | Yes — industry standard |

Any network engineer with a packet capture tool (Wireshark, tcpdump) on the same network segment can intercept a Telnet session and read every character typed — including passwords. SSH encrypts the entire session using asymmetric cryptography (RSA key pair) for key exchange and symmetric encryption for the session itself.

### How SSH Works on Cisco IOS

For SSH to function on a Cisco switch or router, four prerequisites must be met:

1. **Hostname** must be set (not the default "Switch" or "Router")
2. **IP domain name** must be configured
3. **RSA key pair** must be generated — the modulus size determines encryption strength (2048-bit is recommended)
4. **VTY lines** must be configured with `login local` and `transport input ssh`

The hostname and domain name together form the key label (e.g., `SW1.cisco.com`) used to identify the RSA key pair stored on the device.

### RIPv2 — Dynamic Routing for Multi-Hop Reachability

**RIP (Routing Information Protocol) version 2** is a distance-vector dynamic routing protocol. In this lab, it enables Router0 and Router1 to automatically learn each other's directly connected networks and install routes into their routing tables. This allows PC0 (on the 10.0.0.0 network) to reach SW1's SVI (on the 12.0.0.0 network) through two routers — a path that static routing or a simple default gateway alone would not handle automatically.

`no auto-summary` is required with RIPv2 to prevent the protocol from summarizing subnet routes to their classful boundaries — which would cause routing failures in discontiguous or subnetted address spaces.

### Real-World Example

A network operations team manages a Cisco switch in a remote branch. The branch switch is on the 12.0.0.0 network, and the NOC is on the 10.0.0.0 network, separated by a WAN link through two routers. RIPv2 ensures the NOC's router knows how to reach the remote branch network. SSH ensures that when the NOC engineer connects to the switch, the session is fully encrypted — compliant with the company's security policy.

### Advantages of SSH over Telnet

- Encrypted session — no plaintext password exposure
- Supports public key authentication (more advanced deployments)
- Meets compliance requirements (PCI-DSS, HIPAA, ISO 27001) that prohibit Telnet
- Industry standard for all production Cisco device management

### Limitations

- Requires hostname, domain name, and RSA key generation before it can be enabled — slightly more setup than Telnet
- RSA key generation with 2048 bits can take several seconds on lower-end hardware
- SSH version 1.x has known vulnerabilities — always enforce SSHv2 with `ip ssh version 2`

## 5. Step-by-Step Configuration

---

### Device: Router0 — Left Edge Router

```bash
Router> enable
Router# configure terminal
```
**Explanation:** Enters privileged EXEC mode and global configuration mode.

```bash
Router(config)# interface GigabitEthernet0/0
Router(config-if)# ip address 10.0.0.1 255.0.0.0
Router(config-if)# no shutdown
Router(config-if)# exit
```
**Explanation:** Assigns IP address 10.0.0.1/8 to Gi0/0, which faces the ADMIN PC (PC0) on the 10.0.0.0 network. `no shutdown` activates the interface — all router interfaces are administratively down by default.

```bash
Router(config)# interface GigabitEthernet0/1
Router(config-if)# ip address 11.0.0.1 255.0.0.0
Router(config-if)# no shutdown
Router(config-if)# exit
```
**Explanation:** Assigns 11.0.0.1/8 to Gi0/1, which connects to Router1 over the 11.0.0.0/8 transit (WAN) link. This interface is one end of the inter-router link.

```bash
Router(config)# router rip
Router(config-router)# version 2
```
**Explanation:** Enables RIP routing and specifies version 2. RIPv2 supports classless routing (VLSM) and sends subnet mask information in its updates, unlike RIPv1. Always explicitly specify version 2.

```bash
Router(config-router)# network 10.0.0.0
Router(config-router)# network 11.0.0.0
```
**Explanation:** Tells RIP to advertise the 10.0.0.0 and 11.0.0.0 networks to neighboring routers and to listen for RIP updates on interfaces belonging to those networks. Router0 will learn the 12.0.0.0 network from Router1 via RIP.

```bash
Router(config-router)# no auto-summary
Router(config-router)# exit
```
**Explanation:** Disables automatic route summarization. Without this, RIPv2 would advertise classful summaries (e.g., 10.0.0.0/8 summarized to 10.0.0.0/8 — harmless here, but dangerous in subnetted designs). Best practice is always to disable auto-summary with RIPv2.

### Device: Router1 — Right Edge Router

```bash
Router> enable
Router# configure terminal
```

```bash
Router(config)# interface GigabitEthernet0/0
Router(config-if)# ip address 11.0.0.2 255.0.0.0
Router(config-if)# no shutdown
Router(config-if)# exit
```
**Explanation:** Assigns 11.0.0.2/8 to Gi0/0 — the other end of the inter-router transit link. Router0 uses 11.0.0.1 and Router1 uses 11.0.0.2 on this shared segment.

```bash
Router(config)# interface GigabitEthernet0/1
Router(config-if)# ip address 12.0.0.1 255.0.0.0
Router(config-if)# no shutdown
Router(config-if)# exit
```
**Explanation:** Assigns 12.0.0.1/8 to Gi0/1 — the interface facing SW1 and the branch LAN (12.0.0.0 network). This IP becomes the default gateway for SW1.

```bash
Router(config)# router rip
Router(config-router)# version 2
Router(config-router)# network 11.0.0.0
Router(config-router)# network 12.0.0.0
Router(config-router)# no auto-summary
Router(config-router)# exit
```
**Explanation:** Configures RIPv2 on Router1 to advertise the 11.0.0.0 and 12.0.0.0 networks. Router1 will learn the 10.0.0.0 network from Router0 via RIP, enabling full end-to-end routing between the ADMIN PC and the branch switch.

### Device: SW1 — Branch Layer 2 Switch (SSH Management Target)

#### Step 1 — Hostname and SVI Configuration

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW1
```
**Explanation:** Sets the hostname to SW1. This is not optional for SSH — the hostname is a required component of the RSA key label (`SW1.cisco.com`). Without it, `crypto key generate rsa` will produce a key bound to the generic hostname, which is also not ideal.

```bash
SW1(config)# int vlan 1
SW1(config-if)# ip address 12.0.0.100 255.0.0.0
SW1(config-if)# no shutdown
SW1(config-if)# exit
```
**Explanation:** Creates the management SVI on VLAN 1 and assigns IP 12.0.0.100/8. This is the IP address that the ADMIN PC will SSH to. `no shutdown` activates the SVI.

```bash
SW1(config)# ip default-gateway 12.0.0.1
```
**Explanation:** Configures the switch's default gateway pointing to Router1's Gi0/1 interface (12.0.0.1). Without this, SW1 cannot send replies to SSH sessions initiated from the 10.0.0.0 network — the TCP handshake would complete one-way but reply packets would have no route back.

#### Step 2 — SSH Prerequisites

```bash
SW1(config)# ip domain-name cisco.com
```
**Explanation:** Sets the IP domain name on the switch. Combined with the hostname, this forms the fully qualified domain name (FQDN) `SW1.cisco.com`, which is used as the label for the RSA key pair. This step is **mandatory** before RSA key generation.

#### Step 3 — Local User Account Configuration

```bash
SW1(config)# username admin privilege 15 secret cisco123
```
**Explanation:** Creates a local user account with:
- **Username:** `admin`
- **Privilege level 15:** Grants direct privileged EXEC access upon login — the user enters `enable` mode immediately after SSH authentication without needing a separate enable password
- **`secret`:** Stores the password as a salted MD5 hash in the configuration — significantly more secure than `password`, which stores cleartext or weakly encrypted text

> **Important:** In the raw configuration log, the engineer first created the account with `password cisco123` and then tried to add `privilege 15 secret cisco123` to the same username. IOS returned the error:
> ```
> ERROR: Can not have both a user password and a user secret.
> ```
> The fix was to remove the original account with `no username admin password cisco123` before recreating it with `privilege 15 secret cisco123`. See Troubleshooting section.

```bash
SW1(config)# enable password turjo
```
**Explanation:** Sets a privileged EXEC password. Because the admin user is already granted privilege 15, this password is not required for the SSH session in this lab. However, it protects console access and any other sessions that do not use the local database. Note: `enable secret` is preferred over `enable password` in production.

#### Step 4 — RSA Key Generation

```bash
SW1(config)# crypto key generate rsa
```
**Explanation:** Initiates RSA key pair generation. This is what enables SSH on the device — SSH cannot function without an RSA key pair. IOS will prompt for the modulus size.

```
The name for the keys will be: SW1.cisco.com
How many bits in the modulus [512]: 2048
% Generating 2048 bit RSA keys, keys will be non-exportable...[OK]
```
**Explanation:** A 2048-bit key was chosen. The minimum for SSHv2 is 768 bits; 2048 is the current recommended minimum for production. The key is labeled `SW1.cisco.com` — confirming that both hostname and domain name were correctly set. Upon successful key generation, IOS automatically enables SSH (confirmed by the log message `%SSH-5-ENABLED: SSH 1.99 has been enabled`).

#### Step 5 — VTY Line Configuration for SSH

```bash
SW1(config)# line vty 0 8
```
**Explanation:** Enters configuration mode for VTY lines 0 through 8 (9 simultaneous sessions). Note: The switch has 16 VTY lines (0–15); this configuration covers only the first 9. Lines 9–15 remain at their default configuration. In production, configure all 16 lines (`line vty 0 15`) for consistency.

```bash
SW1(config-line)# login local
```
**Explanation:** Configures the VTY lines to authenticate against the local username database. When a user SSHes to SW1, they will be prompted for the username and password defined in the `username admin privilege 15 secret cisco123` entry.

```bash
SW1(config-line)# transport input ssh
```
**Explanation:** Restricts the VTY lines to accept **only SSH connections**. Telnet and all other protocols are blocked. This is the critical security distinction from the previous lab — even if someone attempts `telnet 12.0.0.100`, the connection will be refused. This command enforces encrypted-only remote access.

```bash
SW1(config-line)# exit
```

> **Note:** `do wr` (save configuration) was not captured in the provided input for SW1. Configuration persistence was **Not Provided in Input**.

## 7. Troubleshooting

### Issue 1: Conflicting `password` and `secret` on the Same Username

**Error Message:**
```
SW1(config)# username admin privilege 15 secret cisco123
ERROR: Can not have both a user password and a user secret.
Please choose one or the other.
```

**Root Cause:** The engineer first created the account with:
```bash
SW1(config)# username admin password cisco123
```
Then attempted to add `privilege 15 secret cisco123` to the same username. IOS does not allow a user account to have both a `password` (weakly stored) and a `secret` (hashed) simultaneously. The two storage methods are mutually exclusive.

**Fix Applied:**
```bash
SW1(config)# no username admin password cisco123
SW1(config)# username admin privilege 15 secret cisco123
```
The original account was deleted and recreated with only the `secret` variant and privilege 15.

**Lesson Learned:** Always use `secret` instead of `password` when creating local user accounts. If you need to change a user's authentication method, delete the account first with `no username <name>` before recreating it.

---

### Issue 2: Ambiguous `ex` Command in Line Configuration Mode

**What Happened:**
```
SW1(config-line)# ex
% Ambiguous command: "ex"
```

**Root Cause:** In `line` configuration mode, `ex` matches more than one command. The full command `exit` must be typed.

**Fix Applied:** Entered `exit` in full.

**Lesson Learned:** IOS abbreviation resolution is context-dependent. An abbreviation that works in one mode may be ambiguous in another. When in doubt, type the full command.

---

### Issue 3: `ip domain-name` Entered Incompletely Twice

**What Happened:**
```
SW1(config)# ip dom
SW1(config)# ip domain
```
Both partial entries were rejected before the full `ip domain-name cisco.com` was accepted.

**Root Cause:** Entering IOS commands requires enough characters to uniquely identify the command. `ip dom` and `ip domain` were not sufficient in this context.

**Fix Applied:** The complete command `ip domain-name cisco.com` was entered on the third attempt.

## 9. Notes / Real-World Insights

### Best Practices

- **Always use `ip ssh version 2`** after generating RSA keys.
  ```bash
  SW1(config)# ip ssh version 2
  ```
  SSH 1.99 (shown in the lab output) indicates the device supports both SSHv1 and SSHv2. SSHv1 has known cryptographic vulnerabilities. Enforcing version 2 eliminates SSHv1 negotiation entirely.

- **Always use `secret` over `password` for all accounts.** The `password` keyword stores credentials in reversible cleartext or weak Type-7 encryption. The `secret` keyword uses MD5 hashing (Type-5) or, in newer IOS versions, SHA-256 (Type-9) — significantly harder to crack if the configuration is exposed.

- **Apply `transport input ssh` to all VTY lines (0–15), not just 0–8.** Lines 9–15 left unconfigured may default to accepting Telnet, creating an unintended bypass. Always configure the full range:
  ```bash
  line vty 0 15
  transport input ssh
  login local
  ```

- **Restrict SSH access with an ACL on the VTY lines.** Allow only the management subnet to initiate SSH sessions:
  ```bash
  access-list 10 permit 10.0.0.0 0.255.255.255
  line vty 0 15
  access-class 10 in
  ```

- **Use `no auto-summary` with RIPv2 consistently.** Forgetting this in a production network with subnetted address space will cause routing black holes.

### Common Mistakes

| Mistake | Consequence |
|---|---|
| Forgetting `ip domain-name` before `crypto key generate rsa` | RSA key generation fails or is labeled incorrectly |
| Using `password` instead of `secret` for user accounts | Credentials stored insecurely; vulnerable to config file exposure |
| Configuring VTY lines 0–8 only and leaving 9–15 at defaults | Lines 9–15 may accept Telnet — security policy bypass |
| Not running `ip ssh version 2` | Device negotiates SSHv1 which has known vulnerabilities |
| Forgetting `no auto-summary` in RIPv2 | Route summarization causes reachability failures in subnetted networks |
| Using 512-bit RSA keys | Too small for modern security standards; some SSH clients will refuse the connection |

### SSH vs Telnet 

| Question | Answer |
|---|---|
| What port does SSH use? | TCP 22 |
| What port does Telnet use? | TCP 23 |
| What are the 4 prerequisites for SSH on IOS? | Hostname, domain name, RSA keys, VTY line config |
| What does `privilege 15` on a user account do? | Grants immediate privileged EXEC access — skips the `enable` prompt |
| What is the difference between `secret` and `password`? | `secret` is hashed (MD5/SHA-256); `password` is cleartext or weakly encrypted |
| Why use `no auto-summary` with RIPv2? | Prevents classful summarization that breaks subnetted routing |

### Enterprise Context

In real enterprise networks:

- **Telnet is disabled at the network perimeter firewall** — TCP port 23 is blocked. SSH (TCP 22) is the only permitted management protocol.
- **TACACS+ or RADIUS** replaces local username databases for centralized authentication, authorization, and accounting (AAA) — especially in networks with many devices and many administrators.
- **RSA key sizes of 2048 bits or higher** are mandated by security policies aligned with NIST SP 800-131A.
- **RIPv2 is rarely used in modern enterprise networks** — OSPF or EIGRP are preferred due to faster convergence and scalability. RIPv2 is used in this lab for simplicity and CCNA-level learning.
