
# Dynamic ARP Inspection (DAI) — ARP Spoofing and Man-in-the-Middle Attack Prevention

---

## 1. Lab Title

**Dynamic ARP Inspection: Preventing ARP Spoofing and Man-in-the-Middle Attacks on a Layer 2 Network**

---

## 2. Lab Objective

This lab demonstrates how to configure **Dynamic ARP Inspection (DAI)** on a Cisco Layer 2 switch to protect network clients from ARP spoofing and man-in-the-middle attacks. DAI is built on top of DHCP Snooping and uses the DHCP Snooping Binding Table to validate ARP packets — dropping any ARP reply that claims a MAC-to-IP mapping that does not match a trusted binding entry.

**Skills and concepts practiced:**

- Enabling DHCP Snooping as a prerequisite for DAI
- Enabling Dynamic ARP Inspection on a specific VLAN
- Configuring trusted and untrusted ports for both DHCP Snooping and DAI
- Understanding the relationship between DHCP Snooping and DAI
- Verifying DAI trust states using `show ip arp inspection interfaces`
- Understanding how DAI drops invalid ARP replies at the hardware level
- Configuring a router gateway interface as the foundation for the protected network

## 3. Concept Explanation

### What is ARP and Why is it Vulnerable?

**ARP (Address Resolution Protocol)** is used by hosts to map a known IP address to an unknown MAC address on a local network. When PC-A wants to communicate with the default gateway (10.0.0.1), it broadcasts: *"Who has 10.0.0.1? Tell PC-A."* The router replies with its MAC address, and PC-A stores this mapping in its **ARP cache**.

The fundamental vulnerability of ARP is that it is **stateless and unauthenticated**. Any device on the network can send an unsolicited ARP reply (a "gratuitous ARP") claiming any IP-to-MAC mapping — and the receiving host will believe it and update its ARP cache. An attacker exploits this by sending fake ARP replies that say: *"10.0.0.1 (the gateway) is at MY MAC address."* All client traffic destined for the gateway is then sent to the attacker instead — a classic **man-in-the-middle (MITM)** attack.

### What is Dynamic ARP Inspection?

**Dynamic ARP Inspection (DAI)** is a Cisco IOS security feature that intercepts all ARP packets on untrusted switch ports and validates them against the **DHCP Snooping Binding Table**. If the ARP packet's claimed IP-to-MAC mapping does not match an entry in the binding table, the switch **drops the packet silently**. Only ARP packets arriving on trusted ports (uplinks, router connections) bypass inspection.

### How DAI Works Internally

1. A client receives a DHCP lease. DHCP Snooping records the binding: `{MAC, IP, VLAN, Interface}`.
2. When the client later sends or receives an ARP packet, DAI checks: *"Does this ARP's MAC-to-IP mapping match the binding table entry for this port?"*
3. If yes — the ARP packet is forwarded normally.
4. If no — the ARP packet is dropped. The switch increments its DAI drop counter and can log the event.
5. Ports marked as trusted (server uplinks, router connections) bypass this check entirely — ARP packets are forwarded without validation.

### The Dependency Chain

DAI **requires** DHCP Snooping to be configured first. Without a populated DHCP Snooping Binding Table, DAI has nothing to validate ARP packets against — all ARP packets from DHCP clients would be dropped, breaking network connectivity.

```
DHCP Snooping → Binding Table → DAI validation
```

For hosts with statically assigned IP addresses (not DHCP), DAI can use **ARP Access Control Lists (ARP ACLs)** as a manual binding source. This lab covers DHCP-assigned clients only.

### Real-World Example

A university dormitory network has 500 students on the same VLAN. One student runs an ARP spoofing tool (e.g., Ettercap, arpspoof) to intercept traffic between other students and the default gateway. Without DAI, the attack succeeds — all traffic flows through the attacker's laptop unencrypted. With DAI enabled on the access switch, the fake ARP replies are dropped at the port level before they reach any other client. The attacker's ARP packets never propagate.

### Advantages

- Stops ARP spoofing and MITM attacks at the switch hardware level
- Operates transparently — legitimate ARP traffic is unaffected
- Built on the DHCP Snooping Binding Table — no additional database to maintain for DHCP clients
- Rate-limiting on untrusted ports (15 pps default) provides additional protection against ARP flood attacks
- Can be applied per-VLAN for granular control

### Limitations

- **Requires DHCP Snooping** — hosts with static IPs need ARP ACLs as a manual workaround
- DAI binding table is lost on reload if DHCP Snooping database persistence is not configured
- Incorrectly marking a legitimate uplink as untrusted will cause DAI to drop valid ARP traffic — breaking connectivity for downstream devices
- Rate limiting (15 pps default on untrusted ports) can cause issues in environments with high legitimate ARP rates (large subnets with frequent ARP activity)

## 5. Step-by-Step Configuration

---

### Device: Switch — DHCP Snooping and DAI Configuration

#### Step 1 — Enable DHCP Snooping Globally

```bash
Switch> en
Switch# conf t
Switch(config)# ip dhcp snooping
```
**Explanation:** Enables DHCP Snooping globally. This is the **mandatory prerequisite** for DAI. DHCP Snooping builds the binding table that DAI uses to validate ARP packets. Without this step, DAI has no reference data and will drop all ARP packets on untrusted ports — breaking client connectivity.

#### Step 2 — Mark Fa0/4 and Fa0/5 as Trusted for DHCP Snooping

```bash
Switch(config)# int range fa0/4-5
Switch(config-if-range)# ip dhcp snooping trust
Switch(config-if-range)# exit
```
**Explanation:** Marks Fa0/4 and Fa0/5 as trusted DHCP Snooping ports. DHCP OFFER and ACK messages arriving on these ports are forwarded to clients without inspection. These ports connect to legitimate server infrastructure or uplinks. All other ports remain untrusted — rogue DHCP server responses on those ports are dropped automatically.

#### Step 3 — Enable DHCP Snooping on VLAN 1

```bash
Switch(config)# ip dhcp snooping vlan 1
```
**Explanation:** Activates DHCP Snooping enforcement on VLAN 1. The global enable from Step 1 activates the feature; this command specifies which VLANs it applies to. Without this command, DHCP Snooping does not filter any traffic regardless of the global setting. The DHCP Snooping Binding Table will now be populated as clients receive DHCP leases through the trusted ports.

#### Step 4 — Enable Dynamic ARP Inspection on VLAN 1

```bash
Switch(config)# ip arp inspection vlan 1
```
**Explanation:** Enables DAI on VLAN 1. From this point, every ARP packet received on an untrusted port is validated against the DHCP Snooping Binding Table. If the ARP's claimed MAC-to-IP mapping does not match an entry in the binding table, the packet is dropped. ARP packets on trusted ports (Fa0/4-5) bypass this check.

This single command activates DAI for the entire VLAN — all ports in VLAN 1 are immediately subject to ARP inspection based on their trust state.

#### Step 5 — Mark Fa0/4 and Fa0/5 as Trusted for DAI

```bash
Switch(config)# int range fa0/4-5
Switch(config-if-range)# ip arp inspection trust
Switch(config-if-range)# exit
```
**Explanation:** Marks Fa0/4 and Fa0/5 as trusted for DAI specifically. DHCP Snooping trust and DAI trust are **independent settings** — a port trusted for DHCP Snooping is not automatically trusted for DAI. Both must be configured separately.

Ports marked as DAI trusted have their ARP packets forwarded without inspection. This is necessary for router uplinks and server ports — these devices have legitimate reason to send ARP packets that may not have corresponding DHCP binding entries (e.g., statically configured devices).

> **Note:** An attempt to use `ip inspection trust` was made and rejected:
> ```
> Switch(config-if-range)# ip inspection trust
>                           ^
> % Invalid input detected at '^' marker.
> ```
> The correct command is `ip arp inspection trust`. See Troubleshooting section.

Router> enable

**Explanation:** Assigns IP address 10.0.0.1 with a /8 subnet mask to the router's Gi0/0 interface — the default gateway for the 10.0.0.0/8 network. `no shutdown` brings the interface up. The router's interface connects to the switch on a trusted port (Fa0/4 or Fa0/5), ensuring router ARP traffic bypasses DAI inspection.

## 7. Troubleshooting

### Issue 1: `ip inspection trust` Command Rejected

**What Happened:**
```
Switch(config-if-range)# ip inspection trust
                          ^
% Invalid input detected at '^' marker.
```

**Root Cause:** The engineer attempted to use `ip inspection trust` — which is not a valid IOS command. The correct command is `ip arp inspection trust`. The word `arp` was omitted from the command.

**Fix Applied:** The correct command `ip arp inspection trust` was entered immediately after, which was accepted.

**Lesson Learned:** DAI-related interface commands follow the pattern `ip arp inspection <option>`. The full keyword sequence must be used — there is no shortcut form that drops `arp` from the middle of the command. When a `^` marker appears mid-command, the error is at the word immediately before the marker.

---

### Issue 2: DHCP Snooping Trust and DAI Trust Are Independent

**Observation:** The engineer correctly configured `ip dhcp snooping trust` on Fa0/4-5 (Step 2) and then separately configured `ip arp inspection trust` on the same ports (Step 5). This two-step process is sometimes overlooked.

**Root Cause:** This is expected behavior, not an error. DHCP Snooping and DAI are independent features with independent trust states. A port trusted for DHCP Snooping does not automatically become trusted for DAI.

**Lesson Learned:** When deploying both DHCP Snooping and DAI, trusted ports must be explicitly configured for **both** features separately. A common mistake is configuring only one and then wondering why the other is not working correctly on uplink ports.

## 9. Notes / Real-World Insights

### Best Practices

- **Always configure DHCP Snooping before DAI.** If DAI is enabled without a populated binding table, all ARP traffic from DHCP clients on untrusted ports will be dropped — complete loss of connectivity for those clients.

- **Configure DAI on all VLANs that have DHCP clients:**
  ```bash
  ip arp inspection vlan 10,20,30
  ```

- **Increase the DAI rate limit on ports that serve multiple devices** (e.g., a port connected to another switch or a hub):
  ```bash
  interface fa0/4
  ip arp inspection limit rate 100
  ```
  The default 15 pps is appropriate for a single end device. A port connecting to a downstream switch serving many clients needs a higher limit to avoid legitimate ARP traffic being rate-limited and the port going err-disabled.

- **Enable DAI logging to monitor drop events:**
  ```bash
  ip arp inspection log-buffer entries 1024
  ip arp inspection log-buffer logs 1024 interval 10
  ```

- **For hosts with static IP addresses, use ARP ACLs** to manually define trusted MAC-to-IP bindings that DAI can reference:
  ```bash
  arp access-list STATIC_HOSTS
   permit ip host 10.0.0.50 mac host aabb.cc00.1234
  ip arp inspection filter STATIC_HOSTS vlan 1
  ```

- **Configure DHCP Snooping database persistence** to prevent the binding table — and therefore DAI — from breaking on every reload:
  ```bash
  ip dhcp snooping database flash:/dhcp-snooping.db
  ```

### Common Mistakes

| Mistake | Consequence |
|---|---|
| Enabling DAI before DHCP Snooping binding table is populated | All client ARP packets on untrusted ports are dropped — no connectivity |
| Forgetting `ip arp inspection trust` on uplink ports | Router and server ARP packets are dropped — gateway unreachable for all clients |
| Confusing `ip dhcp snooping trust` with `ip arp inspection trust` | Only one feature's trust is set; the other still treats the port as untrusted |
| Using `ip inspection trust` instead of `ip arp inspection trust` | Invalid command — rejected with `^` error |
| Not increasing rate limits on trunk or downlink ports | Legitimate high-volume ARP traffic causes port to go err-disabled |
| Forgetting DHCP Snooping database persistence | Binding table lost on reload — DAI drops all client ARP until leases are renewed |

### The Full Layer 2 Client Protection Stack

This lab implements two of the three core Layer 2 security controls. The complete stack is:

```
Layer 2 Client Protection Stack
│
├── DHCP Snooping          ← Prevents rogue DHCP servers
│     └── Builds Binding Table (MAC + IP + VLAN + Port)
│
├── Dynamic ARP Inspection ← Prevents ARP spoofing / MITM (this lab)
│     └── Validates ARP against Binding Table
│
└── IP Source Guard        ← Prevents IP address spoofing
      └── Validates source IP/MAC against Binding Table
```

Each layer builds on the DHCP Snooping Binding Table. Deploying all three provides comprehensive protection against the most common Layer 2 client-side attacks.

### ARP Attack Scenarios Addressed

| Attack | Description | DAI Mitigation |
|---|---|---|
| ARP Spoofing / Poisoning | Attacker sends fake ARP replies claiming to be the gateway | DAI validates ARP against binding table; fake entries are dropped |
| Man-in-the-Middle via ARP | All client traffic rerouted through attacker's device | Clients never update ARP cache with attacker's MAC — traffic path remains correct |
| ARP Flood | Attacker sends thousands of ARP packets to degrade switch performance | 15 pps rate limit drops excess; port goes err-disabled after burst threshold |

### Interview and Job Tips

- **"What is the difference between DHCP Snooping and DAI?"** — DHCP Snooping prevents rogue DHCP servers and builds a binding table. DAI uses that binding table to prevent ARP spoofing. One builds the database; the other enforces it.
- **"Why does DAI require DHCP Snooping?"** — Because DAI validates ARP packets against the DHCP Snooping Binding Table. Without it, there is no authoritative source of MAC-to-IP mappings to check against.
- **"What happens if you enable DAI without DHCP Snooping?"** — All ARP packets from DHCP clients on untrusted ports are dropped — clients lose Layer 3 connectivity even if they have valid IP addresses.
- **"How do you handle statically addressed hosts with DAI?"** — Use ARP ACLs to manually define the static MAC-to-IP bindings and apply them with `ip arp inspection filter`.
- Know that `show ip arp inspection interfaces` shows trust states and rate limits, while `show ip arp inspection vlan X` shows forwarded/dropped packet statistics — both are commonly asked about in hands-on interviews and practical exams.
