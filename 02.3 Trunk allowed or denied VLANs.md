# VLAN Trunk Allowed List — Traffic Isolation and Unauthorized VLAN Blocking

---

## 1. Lab Title

**Trunk Port VLAN Filtering: Restricting Unauthorized VLAN Traffic Across Inter-Switch Links**

---

## 2. Lab Objective

This lab demonstrates how to control which VLANs are permitted to traverse a trunk link between two switches using the `switchport trunk allowed vlan` command. The lab also simulates an unauthorized VLAN scenario by introducing rogue VLANs (VLAN 40 and VLAN 50, named HAKER-1 and HAKER-2) and then explicitly restricting them from crossing the trunk.

**Skills and concepts practiced:**

- Creating and naming VLANs manually on a switch
- Assigning access ports to specific VLANs
- Configuring 802.1Q trunk links between switches
- Restricting trunk-allowed VLANs using `switchport trunk allowed vlan`
- Using `switchport trunk allowed vlan except` to block specific VLANs
- Verifying trunk configuration using `show interfaces trunk`
- Understanding the security implications of uncontrolled trunk links

---

## 3. Concept Explanation

### What is a Trunk Allowed VLAN List?

By default, when a port is configured as an 802.1Q trunk, it allows **all VLANs (1–1005)** to pass through. This means any VLAN that exists on the switch can potentially send traffic over that trunk link to the connected switch — including VLANs that should never leave a specific segment.

The `switchport trunk allowed vlan` command gives the network engineer precise control over which VLANs are permitted on a trunk link. Traffic belonging to VLANs not in the allowed list is **dropped at the trunk port** — it never crosses to the other switch.

### Why It Is Used in Real Networks

In enterprise environments, not every switch needs to know about every VLAN. For example:

- A trunk link between a distribution switch and an access switch should only carry the VLANs that the access switch actually needs.
- Keeping unnecessary VLANs off trunk links reduces broadcast domain flooding, limits the blast radius of a misconfiguration, and prevents potential VLAN hopping attacks.

### How It Works Internally

When a frame arrives at a trunk port, the switch checks the VLAN tag in the 802.1Q header against the port's allowed VLAN list. If the VLAN is in the list, the frame is forwarded. If not, it is dropped. This is enforced at the hardware level — it is not a firewall rule, but a switching decision made per-frame.

### Real-World Example

An access-layer switch serves the HR, IT, and CS departments. It connects via trunk to the distribution layer. VLAN 40 was created locally for a test device. By restricting the trunk to only VLANs 10, 20, and 30, the engineer ensures that VLAN 40 traffic never reaches the distribution layer — even if a device on VLAN 40 tries to communicate upstream.

### This Lab's Security Scenario

VLANs 40 (HAKER-1) and 50 (HAKER-2) were deliberately created to simulate rogue or unauthorized VLANs. The lab then demonstrates two methods to block them from crossing the trunk:

- **SW1:** Explicitly allows only VLANs 10, 20, and 30 — replacing the default all-VLAN permit
- **SW2:** Uses the `except` keyword to allow all VLANs except VLAN 50

### Advantages

- Provides granular control over inter-switch VLAN traffic
- Reduces unnecessary broadcast traffic on trunk links (acts like manual pruning)
- Adds a layer of defense against unauthorized VLAN propagation
- Easy to implement and verify

### Limitations

- Does not replace proper VLAN security practices (e.g., disabling unused ports, using private VLANs)
- The `except` keyword on SW2 still allows VLAN 40 (HAKER-1) — partial protection only
- Misconfiguring the allowed VLAN list can accidentally block legitimate traffic and cause outages

## 5. Step-by-Step Configuration

### Device: SW1 — Access Switch with VLAN Filtering on Trunk

#### Phase 1 — Initial VLAN and Port Configuration

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW1
```
**Explanation:** Enters privileged EXEC mode, then global configuration mode. Sets the hostname for identification.

```bash
SW1(config)# vlan 10
SW1(config-vlan)# name IT
SW1(config)# vlan 20
SW1(config-vlan)# name HR
SW1(config)# vlan 30
SW1(config-vlan)# name CS
```
**Explanation:** Creates three VLANs with descriptive names. Without VTP in this lab, VLANs must be manually created on each switch. Naming VLANs makes the network easier to manage and audit.

```bash
SW1(config)# int fa0/1
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 10
```
**Explanation:** Configures Fa0/1 as an access port for VLAN 10 (IT). Access ports carry traffic for only one VLAN and are used to connect end devices.

```bash
SW1(config)# int fa0/2
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 20
```
**Explanation:** Assigns Fa0/2 to VLAN 20 (HR).

```bash
SW1(config)# int fa0/3
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 30
```
**Explanation:** Assigns Fa0/3 to VLAN 30 (CS).

```bash
SW1(config)# int fa0/4
SW1(config-if)# switchport mode trunk
```
**Explanation:** Configures Fa0/4 as an 802.1Q trunk port toward SW2. At this point, the trunk allows all VLANs (1–1005) by default — including any future unauthorized VLANs.

#### Phase 2 — Introducing Rogue VLANs

```bash
SW1(config)# vlan 40
SW1(config-vlan)# name HAKER-1
```
**Explanation:** Creates a simulated unauthorized VLAN 40. In a real scenario, this could represent a rogue device or an unauthorized network segment someone added without approval.

```bash
SW1(config)# int fa0/5
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 40
```
**Explanation:** Assigns Fa0/5 to the rogue VLAN 40. PC6 is connected here, representing an unauthorized user.

```bash
SW1(config)# vlan 50
SW1(config-vlan)# name HAKER-2
SW1(config)# int fa0/6
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 50
```
**Explanation:** Creates a second rogue VLAN 50 and assigns Fa0/6 to it. PC7 is connected here.

#### Phase 3 — Restricting the Trunk to Authorized VLANs Only

```bash
SW1(config)# int fa0/4
SW1(config-if)# switchport trunk allowed vlan 10,20,30
```
**Explanation:** This is the key security command. It **replaces** the default allow-all behavior and restricts the trunk to only carry VLANs 10, 20, and 30. VLAN 40 and VLAN 50 traffic will now be dropped at the trunk port and will not reach SW2. This is the most secure approach — explicitly whitelisting permitted VLANs.

```bash
SW1(config-if)# do wr
```
**Explanation:** Saves the running configuration to NVRAM so the configuration persists after a reload.

```bash

```
**Explanation:** Uses the `except` keyword to allow all VLANs on the trunk **except** VLAN 50 (HAKER-2). The resulting allowed list becomes VLANs 1–49 and 51–1005. ```
**Explanation:** Saves the configuration to NVRAM.

## 7. Troubleshooting

### Issue 1: Incorrect Mode Set on SW2 Fa0/2 Initially

**What Happened:** During initial configuration of SW2, Fa0/2 was briefly set to trunk mode (`switchport mode trunk`) before being corrected to access mode. The `no switchport mode access` command was then used to reset the interface.

**Root Cause:** A typing/logic error during configuration — the engineer intended to configure the port as an access port but mistakenly entered trunk mode first.

**Fix Applied:** The interface was reset using `no switchport mode access` to return it to dynamic auto, and then `switchport mode access` was re-applied correctly.

**Lesson Learned:** Always confirm the intended port role before issuing mode commands. Use `show interfaces fa0/X switchport` to verify the operational mode of a port before moving to the next configuration step.

---

### Issue 2: STP Forwarding State Shows Only VLAN 30 on SW1 Trunk

**What Was Observed:**

```
Port     Vlans in spanning tree forwarding state and not pruned
Fa0/4    30
```

**Root Cause:** This is a Spanning Tree Protocol (STP) state snapshot, not a configuration error. During initial lab convergence in Cisco Packet Tracer, STP may still be in the process of transitioning ports through listening and learning states for multiple VLANs. After full convergence, VLANs 10 and 20 would also appear in forwarding state.

**Fix Applied:** No fix required. This is normal STP behavior during topology convergence in simulation environments.

**Lesson Learned:** Do not confuse the STP forwarding state line in `show interfaces trunk` with the allowed VLAN list. A VLAN not appearing in the forwarding state line is a temporary STP condition — not a configuration error.

## 8. Conclusion

This lab demonstrated two practical techniques for restricting VLAN traffic on trunk links:

- **Explicit whitelist** (`switchport trunk allowed vlan 10,20,30` on SW1): The most secure method. Only named VLANs are permitted — everything else is blocked by default.
- **Blacklist by exception** (`switchport trunk allowed vlan except 50` on SW2): A targeted block that removes a specific VLAN while permitting all others. Less secure than whitelisting, but useful for quick remediation.

The lab also reinforced that trunk ports, by default, carry all VLANs — a significant security exposure if left unmanaged. Controlling the trunk allowed VLAN list is a fundamental practice in any network where VLAN segmentation is used for security or traffic management.

## 9. Notes / Real-World Insights

### Best Practices

- **Always use explicit whitelisting on trunk ports.** Allowing only the VLANs that are actually needed minimizes the attack surface and reduces unnecessary broadcast traffic.
- **Audit trunk allowed VLAN lists regularly.** Over time, VLANs get added and removed. Trunk lists that were correct at deployment can become stale and either overly permissive or overly restrictive.
- **Change the native VLAN from VLAN 1.** The native VLAN (default: VLAN 1) carries untagged traffic on trunk ports. It is best practice to change it to an unused VLAN to mitigate VLAN hopping attacks. This was not configured in this lab.
- **Disable unused ports and place them in an unused VLAN.** A physical port connected to a rogue device is more dangerous than a misconfigured trunk list.

### Common Mistakes

| Mistake | Consequence |
|---|---|
| Using `switchport trunk allowed vlan add X` vs just `vlan X` | `add` appends to the list; omitting `add` replaces the entire list and can accidentally block all traffic |
| Forgetting VLAN 1 in the allowed list | Management traffic may be disrupted if VLAN 1 is accidentally excluded |
| Using `except` when only a few VLANs should be allowed | `except` is a blacklist — it is less secure than an explicit whitelist |
| Not saving config with `wr` or `copy run start` | Configuration is lost on reload |

### Critical Command Distinction

```bash
# REPLACES the entire allowed list — use carefully
switchport trunk allowed vlan 10,20,30

# ADDS to the existing allowed list — safer for incremental changes
switchport trunk allowed vlan add 40

# REMOVES a specific VLAN from the list
switchport trunk allowed vlan remove 40

# BLOCKS specific VLANs, allows everything else
switchport trunk allowed vlan except 50
```
