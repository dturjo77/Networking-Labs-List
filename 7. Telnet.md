# Remote Device Management via Telnet — Switch SVI, Default Gateway, and VTY Line Configuration

---

## 1. Lab Title

**Telnet-Based Remote Access: Configuring Switch Management Interface, VTY Lines, and Local Authentication**

## 2. Lab Objective

This lab demonstrates how to enable remote management access to a Cisco switch using Telnet. It covers configuring a Switch Virtual Interface (SVI) for in-band management, setting a default gateway for inter-network reachability, creating local user credentials, and configuring VTY lines for authenticated Telnet sessions.

The lab also shows that direct Telnet to a router interface is refused by default, and that the SVI IP of the switch is the correct Telnet target for remote switch management.

**Skills and concepts practiced:**

- Configuring router interfaces with IP addresses across multiple networks
- Configuring a management SVI (VLAN 1) on a Layer 2 switch
- Setting a default gateway on a switch for remote reachability
- Creating local username and password credentials
- Configuring an enable (privileged EXEC) password
- Configuring VTY lines for Telnet access with local authentication
- Setting `transport input telnet` on VTY lines
- Verifying Telnet connectivity from remote PCs across a routed network
- Understanding why Telnet to a router interface is refused without VTY line configuration

## 3. Concept Explanation

### What is In-Band Switch Management via Telnet?

A Layer 2 switch does not route traffic — it forwards frames based on MAC addresses. However, it still needs to be managed remotely. To enable this, a **Switch Virtual Interface (SVI)** is created, typically on VLAN 1. The SVI is assigned an IP address, giving the switch a management identity on the network.

**Telnet** is a remote access protocol that opens a command-line session to a network device over TCP port 23. Once a switch has an SVI IP and its VTY (Virtual Terminal) lines are configured, any host that can reach the SVI IP can log into the switch CLI remotely.

### Why It Is Used in Real Networks

In production environments, network engineers rarely have physical console access to every switch or router. Remote management via Telnet (or the more secure SSH) is how day-to-day configuration changes, troubleshooting, and monitoring are performed from a central location — often a Network Operations Center (NOC).

### How It Works Internally

1. A switch SVI is assigned an IP address in the management subnet.
2. A default gateway is configured on the switch so it can respond to Telnet sessions initiated from hosts on other networks (the switch needs to know where to send reply packets).
3. VTY lines (logical remote access channels) are configured with `login local` to require username/password authentication.
4. `transport input telnet` specifies that only Telnet connections are accepted on those VTY lines.
5. A remote PC opens a TCP connection to the switch's SVI IP on port 23, authenticates with local credentials, and enters the switch CLI.

### The Default Gateway Requirement

A switch by itself only knows about its directly connected subnet. If a Telnet session comes from a different network (as in this lab — the HR PC is on the 10.0.0.0 network, and SW2 is on the 11.0.0.0 network), the switch needs to know where to send the TCP reply. The default gateway points the switch toward the router, which handles inter-network routing.

### Real-World Example

A junior network engineer at a company needs to reconfigure access ports on a switch in a remote branch office. Instead of traveling to the site, they Telnet to the switch's management IP from their workstation through the corporate WAN, make the changes, and save the configuration — all without leaving their desk.

### Advantages

- Enables remote CLI management without physical console access
- Simple to configure
- Allows centralized management of distributed network devices

### Limitations

- **Telnet transmits all data — including passwords — in plaintext.** It is not secure and should not be used over untrusted networks.
- In modern enterprise networks, **SSH is the required standard** for remote management. Telnet is used in lab environments for simplicity.
- Without a correctly configured default gateway, remote Telnet from a different subnet will fail silently or time out.

## 5. Step-by-Step Configuration

---

### Device: Router0 — Inter-Network Routing

```bash
Router> enable
Router# configure terminal
```
**Explanation:** Enters privileged EXEC mode and then global configuration mode to begin device configuration.

```bash
Router(config)# interface GigabitEthernet0/0
Router(config-if)# ip address 10.0.0.1 255.0.0.0
Router(config-if)# no shutdown
Router(config-if)# exit
```
**Explanation:** Assigns IP address 10.0.0.1 with a /8 mask to Gi0/0 — the interface connecting to SWITCH-1 and the HR network. `no shutdown` brings the interface up (router interfaces are administratively down by default).

```bash
Router(config)# interface GigabitEthernet0/1
Router(config-if)# ip address 11.0.0.1 255.0.0.0
Router(config-if)# no shutdown
Router(config-if)# exit
```
**Explanation:** Assigns 11.0.0.1/8 to Gi0/1 — the interface connecting to SWITCH-2 (SW2) and the USER network. This IP becomes the default gateway for SW2.

```bash
Router(config)# interface GigabitEthernet0/2
Router(config-if)# ip address 12.0.0.1 255.0.0.0
Router(config-if)# no shutdown
```
**Explanation:** Assigns 12.0.0.1/8 to Gi0/2 — the interface connecting to the ADMIN PC (PC3). The ADMIN PC uses this network to reach and manage SW2 across the routed infrastructure.

> **Note:** In the raw configuration log, the engineer entered the `GigabitEthernet0/2` interface multiple times without issuing any commands before finally adding the IP address. This was a navigation error with no impact on the final configuration.

---

### Device: SW2 — Switch Management and Telnet Configuration

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW2
```
**Explanation:** Enters configuration mode and sets the hostname to SW2 for identification. The hostname appears in the CLI prompt and in Telnet sessions, confirming which device the engineer is connected to.

```bash
SW2(config)# ip domain-name cisco.com
```
**Explanation:** Sets the IP domain name on the switch. While this is required for SSH key generation, it is configured here as part of standard device setup. It has no functional impact on Telnet in this lab.

```bash
SW2(config)# ip default-gateway 11.0.0.1
```
**Explanation:** This is a critical command for remote management. Because SW2 is a Layer 2 switch, it does not run a routing protocol. Without a default gateway, SW2 cannot send TCP reply packets back to hosts on other networks (such as PC0 on 10.0.0.0 or PC3 on 12.0.0.0). This command tells SW2 to send all traffic destined for unknown networks to the router at 11.0.0.1.

```bash
SW2(config)# username admin password cisco123
```
**Explanation:** Creates a local user account with the username `admin` and password `cisco123`. When `login local` is configured on the VTY lines, the switch will require these credentials to authenticate incoming Telnet sessions.

```bash
SW2(config)# enable password turjo
```
**Explanation:** Sets a password required to enter privileged EXEC mode (`enable`) after logging in via Telnet. Without this, a remote user could log in but would be unable to access the full configuration mode. Note: In production, `enable secret` (MD5-hashed) is preferred over `enable password` (stored in cleartext).

```bash
SW2(config)# int vlan 1
SW2(config-if)# ip address 11.0.0.100 255.0.0.0
SW2(config-if)# no shutdown
SW2(config-if)# exit
```
**Explanation:** Creates and activates the management SVI (Switch Virtual Interface) on VLAN 1 with the IP address 11.0.0.100. This is the IP address that remote hosts will Telnet to in order to access SW2's CLI. `no shutdown` brings the SVI up — it is administratively down by default on switches.

```bash
SW2(config)# line vty 0 15
```
**Explanation:** Enters configuration mode for Virtual Terminal lines 0 through 15. These are the logical channels that accept remote connections. Configuring all 16 lines (0–15) means up to 16 simultaneous Telnet sessions can be accepted.

```bash
SW2(config-line)# login local
```
**Explanation:** Instructs the switch to authenticate incoming connections using the local username database (the `username admin password cisco123` account created earlier). Without this command, the switch either accepts connections with no password or refuses them entirely depending on the default configuration.

```bash
SW2(config-line)# transport input telnet
```
**Explanation:** Explicitly specifies that only Telnet connections are accepted on these VTY lines. By default on some IOS versions all input is allowed; this command makes the intent explicit. In a production environment, this would be replaced with `transport input ssh` to enforce encrypted management.

```bash
SW2(config-line)# exit
SW2(config)# do wr
```
**Explanation:** Exits line configuration mode and saves the running configuration to NVRAM. This ensures the Telnet and management configuration persists after a device reload.

## 7. Troubleshooting

### Issue 1: Typo in `login local` Command on SW2

**What Happened:**
```
SW2(config-line)# loging local
% Invalid input detected at '^' marker.
```

**Root Cause:** Typing error — `loging` instead of `login`. The IOS CLI does not attempt to auto-correct misspelled commands.

**Fix Applied:** Re-entered the correct command: `login local`.

**Lesson Learned:** IOS is case-insensitive but not spelling-tolerant. When a `^` marker appears, check the spelling of the command immediately before the marker.

---

### Issue 2: Typo in `hostname` Command on SW1

**What Happened:**
```
Switch(config)# hostnmae SW1
% Invalid input detected at '^' marker.
```

**Root Cause:** Typing error — `hostnmae` instead of `hostname`.

**Fix Applied:** Re-entered as `hostname SW1`.

---

### Issue 3: Connection Refused When Telnetting to Router Interface

**What Happened:** Both PC0 and PC3 initially attempted to Telnet to 11.0.0.2 (which was not even the router's configured IP — the router's Gi0/1 was 11.0.0.1) and received "Connection refused by remote host."

**Root Cause (two separate factors):**
1. The IP 11.0.0.2 does not belong to any configured interface on the router — it is an unreachable address in this topology.
2. Even for the correct router IP (11.0.0.1), the router's VTY lines were never configured in this lab. Without VTY line configuration and a password or `login local`, IOS refuses all incoming Telnet connections by default.

**Fix Applied:** The engineers redirected Telnet to 11.0.0.100 (SW2's SVI), which had VTY lines properly configured.

**Lesson Learned:** There are two separate requirements for Telnet to succeed on a Cisco device: (1) a reachable IP address and (2) configured and enabled VTY lines with authentication. Meeting only one of the two will result in a refused or failed connection.

---

### Issue 4: `ex` Command Ambiguous on Line Configuration Mode

**What Happened:**
```
SW2(config-line)# ex
% Ambiguous command: "ex"
```

**Root Cause:** In line configuration mode, `ex` is ambiguous because it could match both `exit` and potentially other commands. Unlike interface config mode, this mode requires the fuller abbreviation or the full word.

**Fix Applied:** Entered `exit` in full.

**Lesson Learned:** Not all IOS command abbreviations work in every configuration context. When ambiguity errors appear, type the command in full.

---

### Issue 5: Repeated Entry of GigabitEthernet0/2 on Router

**What Happened:** The engineer entered `interface GigabitEthernet0/2` and immediately exited six times before finally assigning an IP address.

**Root Cause:** Likely a copy-paste or navigation error in the Packet Tracer CLI.

**Fix Applied:** Eventually, the IP address `12.0.0.1 255.0.0.0` was assigned and `no shutdown` was applied. No functional impact.

## 8. Conclusion

This lab successfully demonstrated how to enable and verify remote Telnet management of a Cisco Layer 2 switch across a routed network. The key outcomes were:

- A router with three configured interfaces enables communication between three separate IP networks.
- A switch SVI provides an in-band management IP address without requiring a routed interface.
- A default gateway on the switch is essential for remote hosts on different networks to successfully establish and complete a Telnet session.
- Local authentication on VTY lines ensures only authorized users can access the switch CLI remotely.
- The lab confirmed that Telnet to an unconfigured router interface is refused — reinforcing that VTY line configuration is a separate and mandatory step from IP addressing.

## 9. Notes / Real-World Insights

### Best Practices

- **Use SSH instead of Telnet in production.** Telnet sends all data — usernames, passwords, and configuration commands — in plaintext over the network. Anyone with a packet capture tool can intercept the entire session. SSH encrypts the session end-to-end.
- **Use `enable secret` instead of `enable password`.** The `secret` variant stores the password as an MD5 hash in the configuration file. The `password` variant stores it in reversible cleartext (or weak encryption with `service password-encryption`).
- **Restrict VTY access with an ACL.** In production, apply an access-class ACL to the VTY lines to allow Telnet/SSH only from management subnets — not from any host on the network.

  ```bash
  access-list 10 permit 12.0.0.0 0.255.255.255
  line vty 0 15
  access-class 10 in
  ```

- **Create a dedicated management VLAN.** In real networks, management traffic is isolated to its own VLAN (e.g., VLAN 99 or VLAN 100) rather than using the default VLAN 1. This adds a layer of segmentation between user traffic and management access.
- **Always configure `transport input ssh` on VTY lines in production** — never leave it as `all` or `telnet`.

### Common Mistakes

| Mistake | Consequence |
|---|---|
| Forgetting `ip default-gateway` on the switch | Remote Telnet from other networks fails — TCP sessions cannot complete because reply packets have no path |
| Configuring `login` instead of `login local` | Switch prompts for a password but no local database is checked — may allow blank password entry |
| Telnetting to the router interface IP without configuring router VTY lines | Connection refused — the router has no accepting VTY configuration |
| Using `enable password` instead of `enable secret` | Password stored in cleartext or weak encryption in the config file |
| Not saving with `do wr` | Entire configuration lost on device reload |

### Interview and Job Tips

- "What is the difference between `login` and `login local` on a VTY line?" is a standard entry-level interview question. `login` checks against a line password (set with `password <xyz>`); `login local` checks against the local username database.
- Know that `transport input all` is the most permissive setting (allows Telnet, SSH, and others). `transport input none` blocks all remote access. `transport input ssh` is the production standard.
- Understand why a switch needs a default gateway even though it doesn't route: the default gateway is needed for the switch's own IP stack to respond to sessions from remote networks — it does not affect frame forwarding behavior.
- In real enterprise networks, Telnet is often completely disabled at the firewall and switch level. All remote management is conducted over SSH, and access is further controlled by TACACS+ or RADIUS authentication servers (AAA) rather than local credentials.
