# Native VLAN Configuration on 802.1Q Trunk Links

---

## 1. Lab Title

**Native VLAN Hardening: Changing the Default Native VLAN on 802.1Q Trunk Links to Prevent VLAN Hopping**

---

## 2. Lab Objective

This lab demonstrates how to change the native VLAN on 802.1Q trunk ports from the insecure default (VLAN 1) to a dedicated, purpose-built VLAN (VLAN 99). The lab also shows what happens when native VLANs are mismatched between two switches and how to resolve that mismatch.

**Skills and concepts practiced:**

- Creating and naming VLANs including a dedicated native VLAN
- Configuring 802.1Q trunk ports between switches
- Changing the native VLAN on trunk interfaces
- Recognizing and resolving native VLAN mismatch errors
- Understanding Spanning Tree Protocol (STP) port blocking caused by native VLAN inconsistency
- Verifying trunk configuration using `show interfaces trunk`

---

## 3. Concept Explanation

### What is the Native VLAN?

In 802.1Q trunking, all VLAN traffic is **tagged** with a VLAN ID as it crosses the trunk link — except for one VLAN: the **native VLAN**. Traffic belonging to the native VLAN is sent **untagged** across the trunk. On the receiving end, any untagged frames arriving on a trunk port are automatically assigned to the native VLAN.

By default on Cisco switches, the native VLAN is **VLAN 1**.

### Why It Matters in Real Networks

Leaving VLAN 1 as the native VLAN is a well-documented security risk. VLAN 1 is the default management VLAN on Cisco switches and carries STP, CDP, VTP, and other control-plane traffic. It also exists on every switch by default and cannot be deleted.

An attacker with physical or logical access can craft double-tagged 802.1Q frames to send traffic from a VLAN they belong to into the native VLAN — a technique called **VLAN hopping**. Changing the native VLAN to a dedicated, unused VLAN (one with no hosts) closes this attack vector.

### How It Works Internally

When a switch receives an untagged frame on a trunk port, it assigns the frame to the native VLAN. When it sends a frame belonging to the native VLAN out a trunk port, it strips the tag before sending. All other VLANs retain their 802.1Q tag.

Both ends of a trunk link **must agree on the native VLAN**. If they disagree, two problems occur:

1. **CDP Native VLAN Mismatch Warning** — Cisco Discovery Protocol detects and reports the disagreement.
2. **STP PVID Inconsistency** — Spanning Tree Protocol detects that BPDUs are arriving with unexpected VLAN IDs and **blocks the port** to prevent a loop, until the mismatch is resolved.

### Real-World Example

A network security team conducts a quarterly audit and finds that all trunk links still use VLAN 1 as the native VLAN. They create VLAN 99 (named "Native") — a VLAN with no end devices assigned to it — and reconfigure all trunk ports on both ends to use VLAN 99 as the native VLAN. This is applied to both distribution and access switches simultaneously to avoid momentary mismatches.

### Advantages

- Eliminates the default VLAN 1 native VLAN security risk
- Mitigates double-tagging VLAN hopping attacks
- Separates control-plane untagged traffic from user-facing VLANs
- Aligns with Cisco security hardening best practices

### Limitations

- The native VLAN must be configured consistently on **both ends** of every trunk link — a mismatch immediately causes STP port blocking
- VLAN 99 (or whichever VLAN is chosen as native) must be created on all switches that participate in that trunk
- Native VLAN change is a disruptive operation if done on live production trunks without coordination

## 5. Step-by-Step Configuration

---

### Device: SW1 — Core Switch

#### Phase 1 — VLAN Creation

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW1
```
**Explanation:** Enters privileged EXEC mode and global configuration mode. Sets the hostname for identification.

```bash
SW1(config)# vlan 10
SW1(config-vlan)# name IT
SW1(config)# vlan 20
SW1(config-vlan)# name HR
SW1(config)# vlan 99
SW1(config-vlan)# name Native
```
**Explanation:** Creates three VLANs. VLANs 10 and 20 are for user traffic. VLAN 99 is a dedicated native VLAN — it will carry untagged trunk traffic but will have **no end hosts assigned to it**. Creating VLAN 99 before assigning it as native is required; otherwise the switch may warn or refuse the configuration.

#### Phase 2 — Trunk Port Configuration

```bash
SW1(config)# int range fa0/2-3
SW1(config-if-range)# switchport mode trunk
```
**Explanation:** Configures Fa0/2 and Fa0/3 as 802.1Q trunk ports simultaneously using a range command. At this point both ports use the default native VLAN of 1.

**Verification immediately after (before native VLAN change):**

```bash
SW1(config-if-range)# do show interfaces trunk
```

Output observed:
```
Port     Mode   Encapsulation  Status     Native vlan
Fa0/2    on     802.1q         trunking   1
Fa0/3    on     802.1q         trunking   1

Port     Vlans allowed and active in management domain
Fa0/2    1,10,20,99
Fa0/3    1,10,20,99
```
**Explanation:** Confirms trunk links are up. Native VLAN is still 1 on both ports — this is the insecure default state that must be changed.

#### Phase 3 — Changing the Native VLAN

```bash
SW1(config)# int range fa0/2-3
SW1(config-if-range)# switchport trunk native vlan 99
```
**Explanation:** This is the core security command. It changes the native VLAN from VLAN 1 to VLAN 99 on both trunk interfaces. Untagged frames on these trunk ports will now be associated with VLAN 99 instead of VLAN 1.

**Immediately after this command, the following errors appear:**

```
%SPANTREE-2-RECV_PVID_ERR: Received BPDU with inconsistent peer vlan id 1 on FastEthernet0/2 VLAN99.
%SPANTREE-2-BLOCK_PVID_LOCAL: Blocking FastEthernet0/2 on VLAN0099. Inconsistent local vlan.
%SPANTREE-2-RECV_PVID_ERR: Received BPDU with inconsistent peer vlan id 1 on FastEthernet0/3 VLAN99.
%SPANTREE-2-BLOCK_PVID_LOCAL: Blocking FastEthernet0/3 on VLAN0099. Inconsistent local vlan.
```
**Explanation:** SW1 now expects untagged frames on native VLAN 99, but SW2 is still sending BPDUs untagged for VLAN 1. STP detects this PVID inconsistency and immediately blocks the affected ports to prevent a potential loop. This is expected and temporary — it will resolve once SW2 is also reconfigured to match.

**Verification after native VLAN change on SW1 only:**

```
Port     Mode   Encapsulation  Status     Native vlan
Fa0/2    on     802.1q         trunking   99
Fa0/3    on     802.1q         trunking   99

Port     Vlans in spanning tree forwarding state and not pruned
Fa0/2    10,20
Fa0/3    none
```
**Explanation:** Native VLAN is now 99 on both ports. However, VLAN 99 itself is blocked by STP due to the mismatch. Tagged VLANs 10 and 20 are still forwarding on Fa0/2. Fa0/3 shows no VLANs forwarding — still converging.

```bash
SW1(config)# do wr
```
**Explanation:** Saves the running configuration to NVRAM to persist the native VLAN change across reloads.

### Device: SW2 — Access Switch

#### Phase 1 — VLAN Creation

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW2
```

```bash
SW2(config)# vlan 10
SW2(config-vlan)# name IT
SW2(config)# vlan 20
SW2(config-vlan)# name HR
SW2(config)# vlan 99
SW2(config-vlan)# name Native
```
**Explanation:** Same VLAN set as SW1. VLAN 99 must exist on SW2 before it can be assigned as the native VLAN on the trunk ports.

**Verification before native VLAN change (SW2 trunk ports were auto-negotiated):**

```bash
SW2(config)# do show interfaces trunk
```

Output observed:
```
Port     Mode   Encapsulation    Status     Native vlan
Fa0/1    auto   n-802.1q         trunking   1
Fa0/2    auto   n-802.1q         trunking   1
```

**CDP mismatch warnings visible during this phase:**
```
%CDP-4-NATIVE_VLAN_MISMATCH: Native VLAN mismatch discovered on FastEthernet0/1 (1), with SW1 FastEthernet0/2 (99).
%CDP-4-NATIVE_VLAN_MISMATCH: Native VLAN mismatch discovered on FastEthernet0/2 (1), with SW1 FastEthernet0/3 (99).
```
**Explanation:** CDP detects that SW1 has already been changed to native VLAN 99 while SW2 is still on native VLAN 1. This confirms the mismatch and is the trigger to apply the native VLAN change on SW2.

#### Phase 2 — Changing the Native VLAN

```bash
SW2(config)# int range fa0/1-2
SW2(config-if-range)# switchport trunk native vlan 99
```
**Explanation:** Changes the native VLAN to 99 on both trunk ports of SW2. This aligns SW2 with SW1's native VLAN configuration, resolving the mismatch. STP PVID errors will clear automatically once both ends agree.

**Verification after native VLAN change on SW2:**

```
Port     Mode   Encapsulation    Status     Native vlan
Fa0/1    auto   n-802.1q         trunking   99
Fa0/2    auto   n-802.1q         trunking   99

Port     Vlans allowed and active in management domain
Fa0/1    1,10,20,99
Fa0/2    1,10,20,99

Port     Vlans in spanning tree forwarding state and not pruned
Fa0/1    1,10,20,99
Fa0/2    1,10,20,99
```
**Explanation:** Both trunk ports on SW2 now show native VLAN 99. All VLANs are in STP forwarding state, confirming the mismatch is fully resolved and the trunk links are healthy.

## 7. Troubleshooting

### Issue 1: STP PVID Inconsistency — Ports Blocked Immediately After Changing Native VLAN on SW1

**Error Messages:**
```
%SPANTREE-2-RECV_PVID_ERR: Received BPDU with inconsistent peer vlan id 1 on FastEthernet0/2 VLAN99.
%SPANTREE-2-BLOCK_PVID_LOCAL: Blocking FastEthernet0/2 on VLAN0099. Inconsistent local vlan.
```

**Root Cause:** SW1's trunk ports were changed to native VLAN 99, but SW2's trunk ports still had native VLAN 1. SW2 was sending untagged STP BPDUs for VLAN 1. SW1 expected untagged traffic to belong to VLAN 99. The mismatch caused STP to detect an inconsistency and block the affected ports to prevent loops.

**Fix Applied:** Configured `switchport trunk native vlan 99` on SW2's corresponding trunk ports (Fa0/1 and Fa0/2). Once both ends matched, STP automatically unblocked the ports.

**Confirmation of resolution:**
```
%SPANTREE-2-UNBLOCK_CONSIST_PORT: Unblocking FastEthernet0/2 on VLAN0001. Port consistency restored.
%SPANTREE-2-UNBLOCK_CONSIST_PORT: Unblocking FastEthernet0/2 on VLAN0099. Port consistency restored.
```

**Lesson Learned:** When changing the native VLAN on a production trunk, always configure both ends in quick succession — or in a maintenance window. The intermediate state (one end changed, the other not) will cause STP port blocking and temporary traffic loss.

---

### Issue 2: CDP Native VLAN Mismatch Warning

**Warning Message:**
```
%CDP-4-NATIVE_VLAN_MISMATCH: Native VLAN mismatch discovered on FastEthernet0/1 (1), with SW1 FastEthernet0/2 (99).
```

**Root Cause:** Cisco Discovery Protocol runs between directly connected Cisco devices and includes native VLAN information in its advertisements. CDP detected that SW1 was advertising native VLAN 99 while SW2 was still on native VLAN 1 — and immediately reported the discrepancy.

**Fix Applied:** Changing SW2's native VLAN to 99 resolved the mismatch. CDP warnings stopped appearing.

**Lesson Learned:** CDP native VLAN mismatch warnings are useful diagnostic alerts during a partial configuration state. They are not errors on their own but indicate a trunk configuration is incomplete or inconsistent. Always treat this warning as an action item — do not ignore it.

---

### Issue 3: Incomplete `hostname` Command on SW2

**What Happened:** During initial SW2 configuration, the `hostname` command was entered without an argument, producing:
```
% Incomplete command.
```

**Root Cause:** Typing error — the hostname argument was omitted.

**Fix Applied:** Re-entered as `hostname SW2`. No impact on lab outcome.

## 8. Conclusion

This lab demonstrated the complete process of securing trunk links by replacing the default native VLAN (VLAN 1) with a dedicated, purpose-built VLAN (VLAN 99). The key outcomes were:

- A dedicated native VLAN must be **created before it is assigned** to a trunk port.
- Changing the native VLAN on one end of a trunk **immediately causes STP PVID inconsistency** and port blocking until the other end is updated to match.
- CDP provides real-time visibility into native VLAN mismatches — a valuable diagnostic tool during and after configuration.
- Once both ends of the trunk agree on native VLAN 99, STP automatically restores forwarding — no manual intervention required beyond the configuration change.

The lab reinforces that native VLAN security is not theoretical — the STP blocking behavior proves that the switch actively enforces consistency on trunk links.

## 9. Notes / Real-World Insights

### Best Practices

- **Use a dedicated, empty native VLAN.** Choose a VLAN ID that has no end hosts assigned (VLAN 99 in this lab is a common convention). The native VLAN should exist purely to carry untagged trunk frames — it should never be used for user or management traffic.
- **Apply native VLAN changes to both ends simultaneously.** In production, coordinate with a team member to apply the change on both switches at the same time, or schedule a maintenance window. The partial-configuration state causes traffic disruption.
- **Consider tagging the native VLAN as well.** On Cisco switches, you can force the native VLAN to also be tagged using `vlan dot1q tag native` (global command). This means all traffic on the trunk is tagged, eliminating the concept of a native VLAN entirely — the most secure approach.
- **Never use VLAN 1 for any production purpose.** Disable it from all trunk ports if possible, remove it from access port assignments, and change the native VLAN everywhere.

### Common Mistakes

| Mistake | Consequence |
|---|---|
| Changing native VLAN on one switch without immediately updating the other | STP PVID blocking — traffic disruption |
| Using the native VLAN for management traffic (e.g., SVIs) | Management traffic becomes untagged and subject to VLAN hopping |
| Forgetting to create VLAN 99 before assigning it as native | The VLAN does not exist in the active VLAN database; behavior may be inconsistent |
| Ignoring CDP native VLAN mismatch warnings | Indicates a configuration inconsistency that can cause STP issues and security gaps |

### Understanding the Encapsulation Difference

In the output, SW1 shows `802.1q` while SW2 shows `n-802.1q`:

```
SW1 Fa0/2:   on     802.1q     (manually set to trunk)
SW2 Fa0/1:   auto   n-802.1q   (negotiated trunk via DTP)
```

The `n-` prefix indicates the encapsulation was **negotiated** via Dynamic Trunking Protocol (DTP) rather than manually set. In production, it is best practice to set trunk ports to `switchport mode trunk` explicitly (as done on SW1) and disable DTP negotiation with `switchport nonegotiate` to prevent unauthorized trunk formation.

### Interview and Job Tips

- "What is the native VLAN and why should you change it?" is a standard CCNA security question. The answer: it is the VLAN for untagged traffic on a trunk, default is VLAN 1, and it should be changed to an unused VLAN to prevent double-tagging VLAN hopping attacks.
- Know the three VLAN hopping attack types: switch spoofing, single-tagging, and double-tagging. The native VLAN change mitigates the double-tagging variant.
- Be ready to explain why STP blocks a port when native VLANs mismatch — it is not a bug but a deliberate loop-prevention mechanism.
- In large enterprise networks, native VLAN standardization is typically enforced through configuration compliance tools (e.g., Cisco DNA Center, Ansible, or RANCID/Oxidized with diff checks) rather than manual port-by-port audits.
