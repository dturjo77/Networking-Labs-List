## 3. Concept Explanation

### What is VTP?

**VLAN Trunking Protocol (VTP)** is a Cisco proprietary Layer 2 protocol used to centrally manage VLAN information across a network of switches. Without VTP, a network engineer must manually create the same VLANs on every switch — a time-consuming and error-prone process, especially in large enterprise networks.

VTP allows a single switch (the **Server**) to define VLANs, and all other switches in the same VTP domain (the **Clients**) automatically receive and synchronize those VLANs over trunk links.

### Why It Is Used in Real Networks

In enterprise networks with dozens or hundreds of switches, maintaining consistent VLAN databases manually is impractical. VTP eliminates that burden by centralizing VLAN management. When a new VLAN is added to the server, all client switches update automatically — no manual intervention required.

### How It Works Internally

VTP operates by sending **VTP advertisements** over trunk links every 5 minutes or whenever a VLAN change occurs. Each advertisement contains a **configuration revision number**. When a client receives an advertisement with a higher revision number than its own, it updates its VLAN database to match.

There are three VTP modes:

| Mode        | Creates VLANs | Learns VLANs from Server | Forwards VTP Ads | Notes                                      |
|-------------|---------------|--------------------------|------------------|--------------------------------------------|
| Server      | Yes           | Yes                      | Yes              | Default mode; manages the VLAN database    |
| Client      | No            | Yes                      | Yes              | Receives and applies VLAN updates          |
| Transparent | Yes (locally) | No                       | Yes (passes on)  | Maintains its own local VLAN database only |

### Real-World Example

In a campus network, the core switch is configured as VTP Server. All access-layer switches are VTP Clients. When the IT team creates a new VLAN for a new department on the core switch, it propagates to all access switches within seconds — no per-switch configuration needed.

### Advantages

- Reduces administrative overhead in large networks
- Ensures VLAN consistency across all switches
- Simplifies VLAN additions, deletions, and name changes

### Limitations

- A misconfigured switch with a higher revision number can overwrite the entire VLAN database — a common and destructive mistake in production networks
- VTP is Cisco proprietary; not supported in multi-vendor environments
- VTP version 1 and 2 do not support extended VLANs (1006–4094); VTP version 3 is required for that

## 5. Step-by-Step Configuration

---

### Device: SW0 — VTP Server

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW0
```
**Explanation:** Enters privileged EXEC mode, then global configuration mode. Sets the hostname for easy identification.

```bash
SW0(config)# int range fa0/1-2
SW0(config-if-range)# switchport mode trunk
```
**Explanation:** Configures Fa0/1 and Fa0/2 as 802.1Q trunk ports. Trunk links are required for VTP advertisements and multi-VLAN traffic to pass between switches.

```bash
SW0(config)# vtp mode server
```
**Explanation:** Sets this switch as the VTP Server. The server is the authoritative source for the VLAN database in the domain. This is the default mode, but it is best practice to configure it explicitly.

```bash
SW0(config)# vtp domain cisco.com
```
**Explanation:** Defines the VTP domain name. All switches must share the same domain name to exchange VTP advertisements. Switches in different domains do not share VLAN information.

```bash
SW0(config)# vtp pass cisco
```
**Explanation:** Sets a VTP password for authentication. Switches must share the same password to accept VTP updates, providing a basic layer of protection against unauthorized VLAN changes.

```bash
SW0(config)# vtp version 2
```
**Explanation:** Enables VTP version 2. Version 2 adds support for Token Ring VLANs and improved consistency checks compared to version 1. The version must be set on the server; clients inherit it automatically.

```bash
SW0(config)# vlan 10
SW0(config-vlan)# name IT
SW0(config)# vlan 20
SW0(config-vlan)# name HR
SW0(config)# vlan 30
SW0(config-vlan)# name CS
```
**Explanation:** Creates three VLANs on the VTP Server with descriptive names. Because SW0 is the server, these VLANs will automatically propagate to all VTP Client switches in the same domain.

---

### Device: SW1 — VTP Client

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW1
```
**Explanation:** Enters configuration mode and sets the hostname.

```bash
SW1(config)# int range fa0/1-2
SW1(config-if-range)# switchport mode trunk
```
**Explanation:** Sets uplink ports to trunk mode so that VTP advertisements and tagged VLAN traffic can be received from SW0 and passed to SW3.

```bash
SW1(config)# vtp mode client
```
**Explanation:** Sets this switch to VTP Client mode. In this mode, the switch cannot create, delete, or modify VLANs. It only receives and applies updates from the VTP Server.

```bash
SW1(config)# vtp domain cisco.com
SW1(config)# vtp pass cisco
```
**Explanation:** Must match the server's domain name and password exactly. Without matching values, the switch will not accept VTP advertisements.

```bash
SW1(config)# int fa0/3
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 20
```
**Explanation:** Configures Fa0/3 as an access port assigned to VLAN 20 (HR). Access ports carry traffic for a single VLAN and are used to connect end devices such as PCs.

```bash
SW1(config)# int fa0/4
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 30
```
**Explanation:** Configures Fa0/4 as an access port assigned to VLAN 30 (CS).

### Device: SW2 — VTP Client

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW2
```

```bash
SW2(config)# int range fa0/1-2
SW2(config-if-range)# switchport mode trunk
```
**Explanation:** Sets uplink ports to trunk mode for VTP propagation and multi-VLAN traffic.

```bash
SW2(config-if-range)# vtp mode client
SW2(config)# vtp domain cisco.com
SW2(config)# vtp pass cisco
```
**Explanation:** Configures VTP Client mode with matching domain and password. Note: The `vtp version 2` command was attempted but rejected because version changes cannot be made on a VTP Client — only on the Server.

```bash
SW2(config)# int fa0/3
SW2(config-if)# switchport mode access
SW2(config-if)# switchport access vlan 10
```
**Explanation:** Assigns Fa0/3 to VLAN 10 (IT) as an access port for an end device.

```bash
SW2(config)# int fa0/4
SW2(config-if)# switchport mode access
SW2(config-if)# switchport access vlan 20
```
**Explanation:** Assigns Fa0/4 to VLAN 20 (HR) as an access port.

### Device: SW3 — VTP Client

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW3
```

```bash
SW3(config)# int range fa0/1-3
SW3(config-if-range)# switchport mode trunk
```
**Explanation:** SW3 has three uplinks (to SW0/SW1/SW2 and SW4), all configured as trunks to carry multi-VLAN and VTP traffic.

```bash
SW3(config)# vtp mode client
SW3(config)# vtp domain cisco.com
SW3(config)# vtp pass cisco
```
**Explanation:** Configures VTP Client with the correct domain and password. VTP domain was already set from a prior advertisement, as indicated by the "Domain name already set" message — confirming VTP propagation was already working.

---

### Device: SW4 — VTP Transparent

```bash
Switch> en
Switch# conf t
Switch(config)# hostname SW4
```

```bash
SW4(config)# int fa0/1
SW4(config-if)# switchport mode trunk
```
**Explanation:** Only one trunk port (Fa0/1) connects SW4 to SW3. This trunk is needed to pass VTP advertisements through (Transparent mode forwards but does not apply them).

```bash
SW4(config)# vtp mode transparent
```
**Explanation:** Sets this switch to VTP Transparent mode. SW4 will not learn VLANs from the server, and will not synchronize its VLAN database with the domain. However, it will forward VTP advertisements it receives — acting as a pass-through. It maintains its own independent local VLAN database.

```bash
SW4(config)# vtp domain cisco.com
SW4(config)# vtp pass cisco
SW4(config)# vtp version 2
```
**Explanation:** Domain and password are configured for consistency. VTP version 2 can be set on a Transparent switch (unlike on a Client), but it has no effect on VLAN propagation.

```bash
SW4(config)# vlan 50
SW4(config-vlan)# name MN
SW4(config)# vlan 99
SW4(config-vlan)# name DHCP
```
**Explanation:** SW4 creates its own local VLANs (50-MN and 99-DHCP). These VLANs exist only on SW4 and are NOT propagated to any other switch in the domain — this is the defining behavior of VTP Transparent mode.

```bash
SW4(config)# int fa0/2
SW4(config-if)# switchport mode access
SW4(config-if)# switchport access vlan 50
SW4(config)# int fa0/3
SW4(config-if)# switchport mode access
SW4(config-if)# switchport access vlan 99
```
**Explanation:** Assigns access ports to the locally defined VLANs. Fa0/2 serves the PC (VLAN 50 - MN) and Fa0/3 serves Server0 (VLAN 99 - DHCP).

## 7. Troubleshooting

### Issue 1: STP PVID Mismatch Error on Trunk Ports

**Error Message Observed:**
```
%SPANTREE-2-RECV_PVID_ERR: Received 802.1Q BPDU on non trunk FastEthernet0/1 VLAN1
%SPANTREE-2-BLOCK_PVID_LOCAL: Blocking FastEthernet0/1 on VLAN0001. Inconsistent port type.
```

**Root Cause:** This error occurs when one end of a link is configured as a trunk and the other end is still in the default access mode. Spanning Tree detects the mismatch and blocks the port to prevent a loop or VLAN inconsistency.

**Fix Applied:** The trunk configuration was applied to the relevant interface range (`int range fa0/1-2`), which resolved the mismatch and brought the ports back up.

**Lesson Learned:** Always configure both ends of a trunk link simultaneously, or expect temporary STP blocking during the transition.

---

### Issue 2: VTP Version Cannot Be Changed on a Client

**Error Message Observed (SW2):**
```
Cannot modify version in VTP client mode
```

**Root Cause:** VTP version is a global domain setting and can only be changed on the VTP Server. Client switches inherit the version from the server automatically.

**Fix Applied:** No fix needed. The version was already set to 2 on SW0 (the server) and was inherited by all clients.

**Lesson Learned:** Only make VTP version changes on the Server. Attempting to change it on a Client is a no-op in version 1/2 and will produce an error.

---

### Issue 3: SW4 Did Not Receive VLANs 10, 20, 30

**Observation:** After VTP configuration, SW4's `show vlan` output did not display VLANs 10, 20, or 30.

**Root Cause:** This is expected and correct behavior. SW4 is in **VTP Transparent mode**, which means it does not synchronize its VLAN database with the VTP domain. It only passes VTP advertisements through to downstream devices without applying them locally.

**Lesson Learned:** VTP Transparent mode is used intentionally when a switch needs to maintain an independent VLAN configuration — for example, in a DMZ or a segment managed by a different team.

## 8. Conclusion

This lab successfully demonstrated end-to-end VLAN propagation using VTP across a five-switch topology. The key outcomes were:

- **VTP Server (SW0)** centrally defined VLANs 10, 20, and 30, which automatically propagated to all client switches via trunk links.
- **VTP Clients (SW1, SW2, SW3)** received the VLAN database without any manual VLAN creation, confirming that VTP reduces administrative overhead significantly.
- **VTP Transparent (SW4)** demonstrated isolated VLAN management — its locally created VLANs (50 and 99) were not shared with the domain, and it did not adopt the server's VLANs.
- Trunk links are a prerequisite for VTP to function — VTP advertisements only travel over trunk ports.
- VTP domain name and password must match across all participating switches for VTP updates to be accepted.

## 9. Notes / Real-World Insights

### Best Practices

- **Always set a VTP password.** An unprotected VTP domain is vulnerable — any switch plugged into the network with a higher revision number can overwrite the entire VLAN database.
- **Reset the revision number before adding a used switch to a domain.** A second-hand switch with a high revision number can wipe your VLAN database. Reset it by temporarily setting it to Transparent mode, then back to Client/Server.
- **Use VTP version 3 in production.** Version 3 introduces primary server election, extended VLAN support (1006–4094), and protects against accidental VLAN database overwrites.
- **Verify VTP status before and after changes** using `show vtp status` — this shows the domain, mode, version, and the all-important **configuration revision number**.

### Common Mistakes

| Mistake | Consequence |
|---|---|
| Forgetting to set trunk mode on inter-switch links | VTP advertisements won't propagate; VLANs won't sync |
| Mismatched VTP domain name or password | Switch silently ignores VTP updates |
| Adding a high-revision switch without resetting it | Can overwrite the entire VLAN database across all clients |
| Trying to set VTP version on a Client | Command rejected; version must be set on the Server |

### Interview and Job Tips

- Know the difference between all three VTP modes cold — this is a standard interview question for CCNA-level and junior network engineer roles.
- Understand that **VTP Transparent mode forwards but does not apply** VTP advertisements. This is a common trick question.
- Be aware of the **VTP revision number attack** — it is one of the most well-known Layer 2 vulnerabilities and frequently comes up in security-focused interviews.
- In modern enterprise networks, many teams disable VTP entirely and manage VLANs manually or through automation tools (Ansible, Cisco DNA Center) to avoid revision number risks. Be ready to discuss both approaches.
